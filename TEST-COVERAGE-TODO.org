*** Batch 1.5：強化測試（基於 batch 1 抓到的 meta-pattern）  ~半天

**為什麼有這個 batch**：

batch 1 順手抓到 2 個 C++ bug。回頭看那 2 個 bug 都不在「input space
列舉的 N 個點」上、而在**沒列舉的 dimension**：

  Bug 1（裸 modifier 重置 prefix）  → event 生命週期 / 時序 dimension
  Bug 2（Shift + 字母被吃）         → 同 input 兩條 code path 互動 dimension

batch 1 的測試是 interpolation 風（在已知 dimension 上點多採樣）、抓
不到「沒列舉的 dimension」上的 bug。**真強的測試**該在這些被遺漏的
dimension 上加 assertion。

**五個 stronger test 類別**：

| 類別 | 直譯名稱 | 對應 meta-pattern |
|------+----------+--------------------|
| α    | cross-path equivalence | 修 Bug 2 那類 |
| β    | negative assertion     | 修 Bug 1 那類 |
| γ    | cross-modality         | 我們之前完全沒列的 dimension：keyboard × mouse |
| δ    | event lifecycle / timing | Bug 1 同族（更深一層） |
| ε    | roundtrip / invariant 維持 | 整 class 的 universal claim |

**entries**：

- [ ] γ1   Ctrl + click → mouse-click event 應該帶 mods=["ctrl"]    ★★★
- [ ] γ2   Shift + click → 同上、mods=["shift"]                       ★★★
- [ ] β1   裸 modifier press → 後端應**沒**收到 key event             ★★
- [ ] α2   path A / path B post-condition cross-check                  ★★
            (a no-mod、A shift only、a ctrl、A ctrl+shift、
             a ctrl+alt、A ctrl+alt+shift 六種組合一次 sweep、
             斷言 case + mods 完全對齊 SPEC convention)
- [ ] δ1   modifier 提早 release 中斷 prefix                          ★★
            (keydown ctrl、key x、keyup ctrl、key f → 應該不觸發 C-x C-f)
- [ ] γ3   Ctrl+drag → mouse-drag event 帶 mods                       ★
- [ ] γ4   Ctrl+scroll → scroll event 帶 mods                          ★
- [ ] ε1   bind + inject + where-is-command 全 sweep                  ★

**為什麼這幾個 stronger**：

- **γ1 / γ2 / γ3 / γ4 必發現 bug**：讀 =limn_input.cpp= MouseButtonPress
  分支可見、event 完全沒插 mods 欄位（只插 button / page / x / y）。
  C-mouse-1 跟普通 click 在 backend 看起來一模一樣、使用者無從綁定
  modified click。OS-level 寫測試立刻紅、修 5 行立刻綠、之後永遠
  catch。

- **β1 守住剛修的 Bug 1 invariant**：之前是「漏了所以壞」、β1 直接
  assert「不該漏」。寫了之後 future code 任何改動讓裸 modifier 又
  漏出來、立刻紅。

- **α2 守住剛修的 Bug 2 invariant**：六組組合一次 sweep、卡住 path A
  跟 path B post-condition 對齊的 SPEC contract。

- **δ1 探究 batch 1 沒列舉的時序 dimension**：使用者真實 typo 場景。

- **ε1 是 class-wide claim**：不是「測 N 個點」、是「測整個 keymap
  UX chain 的 universal 性質」。

**預期結果**：

  γ1 / γ2 / γ3 / γ4 → 紅（mods 欄位漏插）→ 修 → 綠
  β1 / α2 / δ1     → 多半綠（剛修完應該守住）、若紅代表剛修不完整
  ε1                → 應綠

預估：4 個 entries fail + 修、4 個 entries 一次過。半天工作。

* A. 鍵盤層

** ★ A1. 全鍵盤打字 sweep

怎麼測：
  1. 開 minibuffer (=xdotool key slash=)
  2. =xdotool type "abcdefghijklmnopqrstuvwxyz"= → 驗 minibuffer text
  3. =xdotool type "ABCDEFGHIJKLMNOPQRSTUVWXYZ"= → 驗大寫
  4. =xdotool type "0123456789"= → 驗數字
  5. =xdotool type "!@#$%^&*()_+-=[]{};':\",./<>?"= → 驗符號
  6. submit、驗 defcommand 收到完整字串

為什麼測：
  每個 char 的 X11 keycode 不同、shift modifier 是否被正確 handle、
  Qt key_to_string 的 fallback 分支是否漏掉了某些。空格 bug 那種類型
  的問題、很可能還有同類藏在某個符號上（例如 =`= 變 "BACKTICK"、
  =;= 變 "SEMICOLON" 之類）。

難度：1 小時。

** A2. Backspace 在 minibuffer 刪字

怎麼測：
  1. =xdotool key slash= → open minibuffer
  2. =xdotool type "hellp"=（故意打錯）
  3. =xdotool key BackSpace= 一次
  4. =xdotool type "o"=
  5. submit → 驗 query = "hello"

為什麼測：
  =minibuffer_handle_key= 目前對 BS / TAB / 方向鍵都 =return false=
  讓事件走 global keymap fallback。這代表現在按 BS 在 minibuffer 內**沒
  作用**——這是設計遺漏、不是 by design。應該 BS 刪最後一字、minibuffer-
  input event 帶縮短後的 text。

難度：1 小時。但需要先決定/實作 backend 行為（是 SPEC 補充 + C++ 改）。

** ★ A3. Tab 在 minibuffer（completion 預留）

怎麼測：
  1. open minibuffer
  2. =xdotool key Tab=
  3. 驗 backend 收到 minibuffer-tab event（暫無、需新增 wire event）

為什麼測：
  Tab 對應「completion 觸發」、SPEC §5.4 留了位但沒實作。寫測試先釘
  契約、實作補上。

難度：半天（含 SPEC 補 §5.4、wire event 設計）。

** ★ A4. 方向鍵在 minibuffer 移 cursor

怎麼測：
  1. open minibuffer
  2. =xdotool type "helo"=（漏 l）
  3. =xdotool key Left=（3 次到 e 後面）
  4. =xdotool type "l"=
  5. submit → query = "hello"

為什麼測：
  =buffer/cursor-set= primitive 已有（v0.8 batch 3）、但 minibuffer 內
  方向鍵是否真接到 cursor 還沒驗。如果沒接、就是「primitives 蓋好了
  但沒接線」狀態、要釘住。

難度：1–2 小時。可能需要 C++ 端在 minibuffer_handle_key 加 Left/Right
處理。

** ★ A5. 數字 prefix arg

怎麼測：
  1. 載入 demo init.lisp（j 綁 next-page）
  2. =xdotool type "5"=
  3. =xdotool key j=
  4. 驗 page 從 0 跳到 5（不是 1）

為什麼測：
  SPEC §9.2 寫 =:interactive "p"= 接收 prefix arg、Emacs convention 是
  輸入數字後下個 command 拿到 numeric prefix。今天的 dispatcher 沒這
  機制——5 按下去只觸發 unbound key、然後 j 跳 1 頁。要驗「我們的 p
  interactive spec 真實能用」就要做這條。

難度：半天（涉及 dispatcher 累積 prefix state + 限定機制）。

** ★ A6. Real Emacs-style multi-key prefix C-x C-f

怎麼測：
  1. =(limn:bind "C-x C-f" 'open-file-prompt)=（自定 defcommand）
  2. =xdotool key ctrl+x=
  3. =xdotool key ctrl+f=
  4. 驗 minibuffer 開 prompt "Open file: "

為什麼測：
  我們測過 =g g=（無 modifier 兩鍵 prefix），但**沒測** =C-x C-f= 這種
  「prefix 加 modifier」的常見 Emacs binding。limn/keys lookup-sequence
  應該 handle、但沒實測過。

難度：1 小時。

** A7. Function keys F1–F12

怎麼測：=xdotool key F1= → 驗 backend 收 key event 帶 key="<F1>" 或對等。

為什麼測：F-keys 在 Qt 走特殊 enum、key_to_string 的 default branch
回 "<key-NNN>" 可能讓使用者 bind 不到。

難度：1 小時。

** A8. PageUp / PageDown / Home / End

怎麼測：對應 xdotool key Page_Up / Page_Down / Home / End。

為什麼測：使用者翻頁的另一條入口（除了 j/k）。

難度：1 小時。

** A9. Key repeat / 高頻 input

怎麼測：=xdotool key --repeat 100 --delay 10 j=、驗 page 走 100 次都對。

為什麼測：dispatcher 在快速連發下不能掉 event、不能 reorder。pump
thread 是否 keep up。

難度：1–2 小時。

** A10. 快速交替 jjjkjkjk

怎麼測：=for i in j j j k j k j k; do xdotool key $i; done=、驗
page 在這串後落在預期位置。

為什麼測：A9 是「同一鍵連發」、這是「不同鍵交錯」、再加一層 cancel/
context 切換的壓力。

難度：1 小時。

** A11. Meta key (macOS Cmd / Linux Alt) 語意對齊

怎麼測：=xdotool key alt+x=、驗 backend 收到 mods=["alt"] 或 mods=
["meta"]（看 Limn 怎麼設）。

為什麼測：SPEC 沒明確規範 "meta"、"alt"、"super" 在不同平台對應誰。
Linux X11 上 Alt 是 Mod1、macOS Cmd 是別的。Limn 內部約定 vs OS
真實事件、要對齊。

難度：半天（含 SPEC §6 補充 modifier naming 規範）。

** A12. 三 modifier 組合 C-M-S-x

怎麼測：=xdotool key ctrl+alt+shift+x=、驗 mods 陣列含三者、key="x"。

為什麼測：=key_to_string= / =modifiers_to_array= 在多 modifier 下表
現對不對；特別是 shift 跟 isPrint 的特殊邏輯（v0.8 batch 4 處理過）。

難度：半小時。

** A13. Caps Lock toggle 行為

怎麼測：=xdotool key Caps_Lock=（toggle on）、=xdotool type "abc"=、
驗 minibuffer text = "ABC"。

為什麼測：Caps Lock 是 toggle state、不是 modifier。Qt 對它的處理
可能跟一般 modifier 不同。

難度：1 小時。

** A14. Numpad keys

怎麼測：=xdotool key KP_0/KP_1/.../KP_Add/KP_Enter=、驗 key strings
對。

為什麼測：Numpad 跟 main row 數字鍵 keycode 不同；如果 key_to_string
fallback 走 "<key-NNN>"、使用者 bind "1" 抓不到 numpad 1。

難度：半小時。
