# v0.39 B10 — text-mode self-insert lands

## Root cause (recap from B10-NEXT.md)

`limn/file:find-file` created a Lisp-side fbuf in `*bufs*` but never told
C++ a text buffer existed.  xdotool keystrokes routed to whatever widget
was focused (usually still the PDF view), `mode-buffer-for-window "w1"`
returned the wrong buffer, and printable keys never reached
`self-insert-command`.  Save-buffer then wrote the empty open-time
snapshot back to disk → user thought editing was broken.

## The fix (3 layers, 5 files)

### 1. `backend/limn-file.lisp` — extend the vtable

Added two hooks alongside the existing `*engine-load-fn*` /
`*buffer-set-content-fn*`:

```
*open-text-engine-fn*    (path content) → wire-id or NIL
*fetch-wire-content-fn*  (wire-id)       → string or NIL
```

Plus a new `fbuf` slot `wire-id` (NIL for PDF / unit-tier) and an
accessor `limn/file:buffer-wire-id`.

- `find-file`, for non-PDF kind, calls `*open-text-engine-fn*` after
  fbuf creation; hook errors are swallowed (handler-case) so a wire
  outage still yields a usable Lisp fbuf.
- `save-buffer`, when the fbuf carries a wire-id, calls
  `*fetch-wire-content-fn*` first to pull the live GapBuffer contents
  from C++ (the user has been typing into that, not into the Lisp
  cache).  Falls back to cached content if the fetch returns NIL —
  backwards-compatible with v0.38 unit tests.

### 2. `backend/limn.lisp` — wire the hooks at start

`limn:%install-file-text-bridge` (called from `limn:start` after
`%install-cursor-vtables`) binds the two hooks to real wire impls:

- `*open-text-engine-fn*`:
  1. `bridge/engine-load engine=text win-id=w1` → fresh C++ tid
  2. `buffer/load-file` if path names an existing file (registers
     `buffer_paths[tid]`, which `buffer/save` needs)
  3. caches tid in `limn/text:*current-text-buffer*` synchronously
     (the async `event/buffer-opened` hook does the same, but the
     pump thread can lag behind the next xdotool keystroke — race
     window observed in the W14 driver)
  4. activates `text-mode` on w1's mode-buffer so `%dispatch-key`
     routes printable keys to `self-insert-command`
- `*fetch-wire-content-fn*`: thin `buffer/text` round-trip.

### 3. `backend/limn-text-mode.lisp` — RET + TAB self-insert

The text-mode keymap had no `RET` binding, so newlines fell on the
floor.  Two changes:
- bound `RET` to `self-insert-command`
- extended `self-insert-command`'s key→char dispatch to recognise
  `"RET"` → `#\newline` and `"TAB"` → `#\tab` (mirroring the existing
  `"SPC"` → space special case).

### 4. `sioyek/pdf_viewer/limn_input.cpp` — LF/CR/Tab key naming

`xdotool type "a\nb"` feeds the raw LF byte (0x0A); Qt reports
`ev->text()=="\n"` (not printable → falls past the early return) and
`ev->key()==10` (the latin1 code, **not** `Qt::Key_Return = 0x01000004`),
so the default switch emitted `"<key-10>"` which no keymap binds.
Added an early `ev->text()` check that maps `\n` / `\r` → `"RET"`,
`\t` → `"TAB"`, `\b` → `"BS"`, `0x1B` → `"ESC"` before the switch.

### 5. `backend/tests/unit/file-io-v024.lisp` — 7 regression assertions

Per [[feedback-fix-discipline]]:
- hook fires for text path with correct args
- hook NOT called for PDF path
- new (non-existent) files still fire hook with empty content
- hook error doesn't abort find-file (fbuf still created, wire-id NIL)
- save-buffer fetches via wire when wire-id present
- save-buffer falls back to cached content when fetch returns NIL
- save-buffer skips fetch entirely for PDF buffers

## Remaining PARTIALs (NOT B10)

- **W16** — CJK direct keystroke input via xdotool relies on
  XSendKeyEvent which loses Unicode; needs IM/clipboard path
- **W17** — kill / yank cross-buffer; the kill ring + region-grab
  flow doesn't yet bridge two text buffers
- **W20 A.2** — `(limn/buffer:list)` returns NIL because the wire
  side's `buffer/list` doesn't include text buffers from the
  `*by-path*` registry (B9 namespace split — partially closed by B10
  but not fully)
- **W30** — auto-revert (B17 structural)
- **W04 / W05** — pre-existing pre-B10 partials (TOC deadlock + B6
  crash flake); W04 driver now crashes mid-run rather than completing
  partially.  Not a B10 regression.
