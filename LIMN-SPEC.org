* Limn 規格書 v0.5

Limn 是一個由 Common Lisp（SBCL）控制的顯示框架。
Backend（Lisp）透過 Bridge（Unix socket + JSON）驅動 Frontend（Qt）。

Qt 是目前唯一的 Frontend 實作，但架構設計為可替換：
GTK、terminal（sixel）、headless 等均可實作同一套 Bridge 協議。

** 一、核心概念

| 概念    | 定義                                           | 類比                  |
|---------+------------------------------------------------+-----------------------|
| frame   | OS 層級的獨立視窗                              | Emacs frame           |
| window  | frame 內的視埠，顯示一個 buffer                | Emacs window          |
| buffer  | Limn 的基本內容單元，持有內容與其狀態          | Emacs buffer          |
| engine  | 處理特定類型 buffer 的後端機器                 | Emacs 沒有直接對應    |
| mode    | buffer 的 keymap + hook + 行為集合（細節 §1.1） | Emacs major/minor mode |

關係：

#+begin_src
frame  ──包含──▶  window（可分割為多個，含 floating window）
window ──顯示──▶  buffer（多個 window 可顯示同一個 buffer）
buffer ──由────▶  engine 管理（一種 engine 可管理多個 buffer）
buffer ──套用──▶  mode（一個 major、零或多個 minor，決定使用者怎麼互動）
#+end_src

*** 1.1 模式（Mode）

Mode 是「在這個 buffer 裡按某個鍵會怎樣」的命名 bundle：

- 一個 keymap（可繼承 parent keymap）
- enter / exit hooks
- 可選的 buffer-local 變數
- 用於 modeline 顯示的短名

每個 buffer 有**恰好一個** major mode 與 **零個以上** minor modes。
Keymap 查詢順序：minor modes（依啟用順序新到舊）→ major mode → global。

**Mode 與 engine 不同**：engine 決定 buffer **裝什麼內容**（PDF？HTML？
純文字？），mode 決定 buffer **使用者怎麼互動**。同一個 PDF buffer
可以套 =pdf-mode= 或 =presentation-mode=，內容不變、互動規則換了。

Mode 的定義跟切換邏輯都在 backend；frontend 只透過 =modeline/set= 等
指令更新 chrome 顯示。Mode 系統的 Backend 端慣例見 §9.1。

*** 1.2 Chrome primitives

「Chrome」指 framework 本身的視覺零件，跟 buffer 內容區分。任何 Limn
frontend 必須提供四個 chrome 元素，**前三個是 text-engine buffer，第
四個是 window 的顯示屬性、不是 buffer**——這個區別跟 Emacs 一致。

**Buffer-backed chrome（三個）**：

- **Minibuffer**：universal input prompt。=M-x=、=/=、=C-x C-f=、=M-:=
  等所有從使用者讀字串的場景共用同一個 buffer，有保留 ID
  =*minibuffer*=，有自己的 keymap（=minibuffer-mode=）。指令見 §5.4。
- **Echo area**：minibuffer 閒置時的同一條畫面區域，印 message / error /
  hint。是 buffer，保留 ID =*echo-area*=；內容是「目前要顯示的單行」，
  =message/echo= 寫進去同時也 append 到 =*messages*=。對應 Emacs 的
  =\ *Echo Area 0*= / =\ *Echo Area 1*=（前綴空格的 hidden buffer，且
  做 double-buffering——後續優化）。
- ***Messages***：累積所有 message 的 buffer，保留 ID =*messages*=。可
  以用 =buffer/text :|buffer-id| "*messages*"= 直接拿歷史。

三者統一好處：使用者跟 framework 都用同一套 =buffer/*= 指令訪問，未來可
以套 mode（=messages-mode=、=minibuffer-mode=）、可以用 =view/overlays=
高亮、可以無痛 redirect 到任何其他 text-engine 用例。

**Window decoration（不是 buffer）**：

- **Modeline**：每個 window 底部一條 status line，顯示**關於 buffer**
  的資訊（mode 名、buffer 名、scroll 位置等）。**不**是 buffer——是
  per-window 的 format string，與 Emacs 的 =mode-line-format= 對應；
  同個 buffer 在不同 window 可有不同 modeline。指令見 §5.6。

Text engine 是 bundled engine 之一，所以以上三個 buffer 一律存在、可
透過 =buffer/text= 訪問。詳見 §7.6。

** 二、架構

Limn 是一個 async event-driven loop，概念上類似 REPL，但不是嚴格的
sequential READ→EVAL→PRINT→LOOP。事件異步抵達、可以排隊；
多個 EVAL/PRINT 可以並行進行，靠 request id 對應結果。

#+begin_src
READ  → events 從 Frontend 異步抵達，可排隊
          → Bridge 推送給 SBCL

EVAL  → Lisp handler 處理事件
          → Bridge 送出一個或多個指令（可與其他 event 的 EVAL 並行）

PRINT → Frontend 執行指令，更新畫面
          → Bridge 以相同 id 回傳結果給 SBCL
#+end_src

整體結構：

│  │  (SBCL)  │◀──▶│  Unix socket  │◀──▶│  (Qt 或其他)  │   │

*** 訊息處理與並行

Bridge 的 request/response 設計（每條訊息帶唯一 =id=）允許
SBCL 同時有多個 pending request，不須依序等待。

SBCL 端如何處理並行（單一訊息迴圈、thread pool 等）
屬於 backend 實作細節，本規格不強制規定。
若某個 request 需要長時間運算，backend 應在獨立執行緒中處理，
避免阻塞主事件迴圈。

*** 嵌入模式（Embedding Mode）◇ 長期目標

目前 Bridge 透過 Unix socket 傳遞訊息。未來可加入嵌入模式：
SBCL 透過 CFFI 直接呼叫 Frontend 的 C 函式，
繞過 socket 序列化，適用於需要極低延遲的場景（如即時渲染回饋）。

嵌入模式與 socket 模式使用相同的邏輯 API，
差別僅在傳輸層。切換時 backend 程式碼無需改寫。

** 四、Bridge 協議

*** 4.1 傳輸層

- 協議：Unix domain socket
- 路徑：=/tmp/limn-<PID>=（含 PID 以支援同時跑多個 Limn 實例）
- 格式：UTF-8，每行一個 JSON 物件（以 =\n= 分隔）
- 方向：雙向，同一條連線

*** 4.2 訊息類型

**** Request（Backend → Frontend）

#+begin_src json
{"id": "r42", "cmd": "view/set", "win-id": "w1", "page": 5}
#+end_src

- =id=：唯一字串，由 Backend 生成
- =cmd=：指令名稱
- 其餘欄位為指令參數

**** Response（Frontend → Backend）

#+begin_src json
{"id": "r42", "ok": true,  "data": { ... }}
{"id": "r42", "ok": false, "error": "page out of range"}
#+end_src

*規則*：所有成功回應的 payload 一律放在 =data= 欄位下，即使只有一個欄位。
即使不需要回傳資料，=data= 可省略（=={"id":"r1","ok":true}== 合法）。
失敗回應的 =error= 是字串，描述具體原因。

**** Event（Frontend → Backend，主動推送，無 id）

#+begin_src json
{"event": "key", "frame-id": "f1", "key": "j", "mods": []}
#+end_src

所有事件都帶 =frame-id=，表示事件來源的 OS 視窗。
需要指明具體視窗的事件（如 mouse-click）同時帶 =win-id=。

*** 5.1 bridge/ ── 視窗、frame、engine 管理

// 載入 engine，開啟 buffer
{"id":"r1", "cmd":"bridge/engine-load",

// 在真實 GUI 模式下，=bridge/win-split= 必須產生實際可見的視窗分割

{"cmd":"bridge/frame-new"}
{"cmd":"bridge/frame-close", "frame-id":"f1"}

*** 5.2 view/ ── 視埠顯示

所有 engine 都必須實作。=win-id= 決定路由到哪個 engine。

=view/set= 的通用欄位（所有 engine 適用）：

| 欄位       | 類型  | 說明                    |
|------------+-------+-------------------------|
| =page=     | int   | 頁碼（0-based）         |
| =offset-y= | float | 垂直捲動（文件座標）    |
| =offset-x= | float | 水平捲動（文件座標）    |
| =zoom=     | float | 縮放倍率                |

Engine 專屬參數放在 =engine-params= 中，engine 自行解讀，
不認識的欄位忽略：

#+begin_src json
// 設定視埠（通用欄位 + engine 專屬參數）
{"id":"r10", "cmd":"view/set", "win-id":"w1",
             "page":5, "zoom":1.5,
             "engine-params":{"dark-mode":true, "rotation":90}}
→ {"id":"r10", "ok":true}

// 查詢視埠狀態
{"id":"r11", "cmd":"view/get", "win-id":"w1"}
→ {"id":"r11", "ok":true,
   "data":{"buffer-id":"b1", "page":5, "offset-y":1234.5,
           "zoom":1.5, "engine-params":{"dark-mode":true}}}

// 疊加層（Lisp 決定畫什麼，engine 負責畫）
{"id":"r12", "cmd":"view/overlays", "win-id":"w1",
             "layers":[
               {"type":"rect",
                "page":5, "rect":[x0,y0,x1,y1],
                "color":"#FFD700", "opacity":0.4},
               {"type":"rect",
                "page":5, "rect":[x0,y0,x1,y1],
                "color":"#FF6B6B", "opacity":0.6},
               {"type":"line",
                "page":5, "from":[x1,y1], "to":[x2,y2],
                "color":"#0000FF", "width":2, "opacity":1.0},
               {"type":"text",
                "page":5, "pos":[x,y], "text":"Note",
                "color":"#000000", "size":12, "opacity":1.0}
             ]}
→ {"id":"r12", "ok":true}
#+end_src

=view/overlays= 支援的 type：=rect=、=line=、=text=。
所有 type 都支援 =color=（hex RGB）與 =opacity=（0.0–1.0）。
這是 Lisp 控制視覺呈現的核心原語，所有 engine 都必須實作。

*** 5.3 buffer/ ── buffer 內容操作

engine 依能力實作。=buffer/open= 回應中的 =supports= 欄位
列出該 engine 支援哪些 buffer/ 指令。

#+begin_src json
// 開啟內容，建立 buffer
{"id":"r20", "cmd":"buffer/open",
             "engine":"mupdf", "path":"/tmp/paper.pdf"}
→ {"id":"r20", "ok":true,
   "data":{"buffer-id":"b1", "page-count":42,
           "supports":["buffer/toc","buffer/text",
                       "buffer/links","buffer/render"]}}

{"id":"r21", "cmd":"buffer/close", "buffer-id":"b1"}

// 目錄 / 結構
{"id":"r30", "cmd":"buffer/toc", "buffer-id":"b1"}
→ {"id":"r30", "ok":true,
   "data":[{"title":"Chapter 1","page":0,
            "children":[{"title":"1.1","page":2,"children":[]}]}]}

// 頁面文字（含邊界框，供 Lisp 做搜尋）
// 注意：不適用於 audio、video 等非文字 engine
{"id":"r31", "cmd":"buffer/text", "buffer-id":"b1", "page":5}
→ {"id":"r31", "ok":true,
   "data":{"words":[{"text":"hello","rect":[x0,y0,x1,y1]}, ...]}}

// 連結
{"id":"r32", "cmd":"buffer/links", "buffer-id":"b1", "page":5}
→ {"id":"r32", "ok":true,
   "data":[{"type":"internal","dest-page":12,"rect":[x0,y0,x1,y1]},
           {"type":"uri","uri":"https://...","rect":[x0,y0,x1,y1]}]}

// 整頁渲染 → PNG base64
{"id":"r40", "cmd":"buffer/render",
             "buffer-id":"b1", "page":5, "dpi":150}
→ {"id":"r40", "ok":true, "data":{"png":"iVBORw0K..."}}

// 矩形截圖
{"id":"r41", "cmd":"buffer/render-region",
             "buffer-id":"b1", "page":5,
             "rect":[x0,y0,x1,y1], "dpi":150}
→ {"id":"r41", "ok":true, "data":{"png":"..."}}

// Metadata
{"id":"r42", "cmd":"buffer/metadata", "buffer-id":"b1"}
→ {"id":"r42", "ok":true,
   "data":{"title":"...","author":"...","page-count":42,"format":"pdf"}}
#+end_src

**Buffer 編輯**（text engine 適用；非文字 engine 一律回 =not supported=）：

文字類 buffer 有一個 cursor (offset，0-based 字元位置)。編輯指令以
cursor 跟 range 為核心、跟所有 text-engine buffer 通用——=*minibuffer*=、
=*messages*= 之類的 chrome buffer 跟使用者透過 =engine=text= 開的 buffer
共用同一套協議。

#+begin_src json
// Cursor 查 / 設
{"id":"r50", "cmd":"buffer/cursor-get", "buffer-id":"*minibuffer*"}
→ {"id":"r50", "ok":true, "data":{"offset":3}}

{"id":"r51", "cmd":"buffer/cursor-set",
            "buffer-id":"*minibuffer*", "offset":0}

// 在 cursor 處插入文字並推進 cursor
{"id":"r52", "cmd":"buffer/insert",
            "buffer-id":"*minibuffer*", "text":"foo"}

// 在指定 offset 插入（cursor 在該 offset 之前的話不動，之後的話跟著推）
{"id":"r53", "cmd":"buffer/insert",
            "buffer-id":"*minibuffer*", "at":0, "text":"prefix:"}

// 刪除 [from, to) 範圍
{"id":"r54", "cmd":"buffer/delete",
            "buffer-id":"*minibuffer*", "from":3, "to":5}
#+end_src

這些指令是 text engine 的 SHOULD 實作（§7.2）。對 mupdf 之類非編輯型
engine 一律回 =ok:false= + =error: "not supported"=。

*** 5.4 minibuffer/ ── universal input prompt

Minibuffer 是 framework 的單行輸入區（chrome primitive，見 §1.2）。所有
從使用者讀字串的場景——=M-x=、=/=、=C-x C-f=、=M-:=——都共用同一個 widget。

#+begin_src json
// 打開 minibuffer 並設定 prompt
{"id":"r60", "cmd":"minibuffer/open", "prompt":"/"}
→ {"id":"r60", "ok":true}

// 已開啟下更換 prompt
{"id":"r61", "cmd":"minibuffer/set-prompt", "prompt":"Search: "}

// 替換目前文字（completion / history 回填）
{"id":"r62", "cmd":"minibuffer/set-text", "text":"hello world"}

// 關閉（不論使用者送出 / 取消，backend 都應呼叫一次收尾）
{"id":"r63", "cmd":"minibuffer/close"}

// 查詢狀態
{"id":"r64", "cmd":"minibuffer/get"}
→ {"id":"r64", "ok":true,
   "data":{"open":true, "prompt":"/", "text":"hello"}}
#+end_src

使用者在 minibuffer 中的按鍵會經 =minibuffer-input= / =minibuffer-submit=
/ =minibuffer-cancel= 事件推回 backend（細節見 §六）。

*** 5.5 message/ ── echo area + =*Messages*= buffer

Echo area 是 minibuffer 閒置時的同一條畫面區域，印短訊息；=*Messages*=
是累積所有 message 的 text-engine buffer。

#+begin_src json
// 印一行到 echo area（覆蓋上一條）；自動 append 到 *Messages*
{"id":"r70", "cmd":"message/echo",
            "text":"Saved /tmp/x.pdf"}

// 只 append 到 *Messages*、不打擾 echo area（背景訊息）
{"id":"r71", "cmd":"message/log",
            "text":"Background search: 3 hits in page 5"}

// 清空 echo area（不影響 *Messages* 歷史）
{"id":"r72", "cmd":"message/clear"}
#+end_src

*** 5.6 modeline/ ── window status line

每個 window 底部一條 status line。三段：left（buffer 資訊）、middle（mode
名）、right（位置、百分比等）。

#+begin_src json
// 設定某 window 的 modeline（win-id 省略 = 全域樣板）
{"id":"r80", "cmd":"modeline/set",
            "win-id":"w1",
            "left":  "PDF: paper.pdf",
            "middle":"pdf-mode",
            "right": "p5/42 (12%)"}

// 查詢目前 modeline
{"id":"r81", "cmd":"modeline/get", "win-id":"w1"}
→ {"id":"r81", "ok":true,
   "data":{"left":"...", "middle":"...", "right":"..."}}
#+end_src

v0.4：三段都是純文字。將來可能支援 face / 格式化欄位（如時間、icon）。

** 六、事件參考

Frontend 主動推送，無 =id=。所有事件帶 =frame-id=（事件來源的 OS 視窗）。
需要指明具體視窗的事件額外帶 =win-id=。

*** 輸入事件

#+begin_src json
// 鍵盤
{"event":"key",
 "frame-id":"f1", "key":"j", "mods":[]}
{"event":"key",
 "frame-id":"f1", "key":"s", "mods":["ctrl"]}

// 輸入法（IME）：CJK 及其他複合輸入完成時送出
{"event":"ime-commit",
 "frame-id":"f1", "text":"你好"}

// 語音/AI 音訊輸入：外部語音辨識將結果送回 SBCL
// text 為辨識結果字串，由 backend 決定如何解讀（指令或內容）
{"event":"audio-input",
 "frame-id":"f1", "text":"scroll down to page five"}

// 滑鼠點擊（附文件座標）
// page 在真實 GUI 模式 MUST 由 widget 座標反推實際所在頁碼；
// x / y 為該頁內 0.0–1.0 的歸一化座標。

*** Minibuffer 事件

Minibuffer 開啟時（=minibuffer/open= 之後），使用者輸入的處理規則：

- **printable 字元** → frontend 內部把字元 append 到 minibuffer 文字，
  推 =minibuffer-input= 事件帶當前完整文字；**不**推 =key= 事件。
- **RET** → 推 =minibuffer-submit= 事件帶最終文字；**不**推 =key= 事件。
- **ESC** → 推 =minibuffer-cancel= 事件；**不**推 =key= 事件。
- **其他鍵**（modifier combos、function key、方向鍵）→ 推一般 =key=
  事件。這樣 backend 仍能透過 minibuffer-mode keymap 或 global keymap
  處理（例如 =C-g= 取消、=Up/Down= 歷史導覽）。

#+begin_src json
// 每打一個 printable 字元
{"event":"minibuffer-input",
 "frame-id":"f1", "text":"hel"}

// RET 送出
{"event":"minibuffer-submit",
 "frame-id":"f1", "text":"hello"}

// ESC 取消
{"event":"minibuffer-cancel",
 "frame-id":"f1"}
#+end_src

** 七、Engine Interface Spec

任何人都可以為 Limn 寫 engine。以下是合法 Limn engine 的介面規格。

*** 7.1 MUST 實作

#+begin_src
buffer/open      接受 path 或 url，回傳 buffer-id 與 supports 列表
buffer/close     釋放資源
view/set         更新視埠（至少支援 page、zoom、offset-y）
view/get         回傳目前視埠狀態（含 engine-params）
view/overlays    在視埠上繪製疊加層（rect、line、text，支援 opacity）
                 真實 GUI 模式下 *必須實際繪製* 到 widget；
                 headless / test 模式可只追蹤 layer 數量供 test/snapshot 用
#+end_src

*** 7.2 SHOULD 實作

#+begin_src
buffer/text          文字內容與邊界框（文字類 engine）
buffer/toc           結構/目錄樹
buffer/links         頁面連結
buffer/render        整頁 PNG 渲染
buffer/render-region 矩形 PNG 渲染
buffer/metadata      title、author 等

# 編輯類（text engine 適用，§5.3 後段）
buffer/cursor-get    取得當前 cursor offset
buffer/cursor-set    設定 cursor offset
buffer/insert        在 cursor 或指定 offset 插入文字
buffer/delete        刪除指定 range
#+end_src

=buffer/text= 不適用於 audio、video、image 等非文字 engine。
編輯類指令僅適用於 text engine（如 =mupdf= 即為唯讀）。
engine 對不支援的指令一律回傳 ={"ok":false,"error":"not supported"}=。

*** 7.3 能力宣告

=buffer/open= 回應必須包含 =supports= 欄位：

#+begin_src json
{"ok":true,
 "data":{
   "buffer-id":  "b1",
   "page-count": 42,
   "format":     "pdf",
   "supports":   ["buffer/text","buffer/toc","buffer/links",
                  "buffer/render","buffer/render-region","buffer/metadata"]
 }}
#+end_src

*** 7.4 MUST 推送的事件

#+begin_src
buffer-opened   buffer 成功載入後
error           任何內部錯誤
#+end_src

*** 7.5 Engine 命名慣例

engine 名稱：小寫字母加連字號，如 =mupdf=、=web=、=text=、=sgf=。
對應的 Lisp 封裝使用 CL package，如 =limn/mupdf=、=limn/web=。

*** 7.6 Bundled Engines（frontend 必須 bundle）

任何 Limn frontend 至少 bundle 以下 engine，提供 chrome primitives 與
PDF 基本能力：

- **=text=**：純文字 buffer。最小實作即可（QPlainTextEdit-style）。
  支援 =buffer/text=、=buffer/render=（可選），主要透過 =minibuffer/*=、
  =message/*=、=modeline/*= 三個命名空間間接驅動。**所有 chrome
  primitives**（minibuffer、echo area、modeline、=*Messages*=）都是
  text-engine buffer——這個對稱讓 framework 不必特別處理「框架內部」
  vs「使用者內容」的區別。

- **=mupdf=**：PDF / EPUB 等基於頁的文件。實作完整 §7.1 + §7.2。

=bridge/capabilities= 回應的 =engines= 欄位必須包含這兩個。

** 八、測試協議（Testing Protocol）

Frontend 在 =--test-mode= 旗標下啟用一組額外指令，命名空間為 =test/=。
正式部署時不應啟用。這些指令的目的：讓自動化測試可以「假裝」輸入事件發生，
不需要真的有滑鼠/鍵盤/觸控板。

*** 8.1 啟用方式

#+begin_src bash

={"ok":false, "error":"test mode disabled"}=。

*** 8.3 設計原則

- 每個 inject 指令對應一種 event，型別與正常 event 完全相同

- =--test-mode= 也應該關閉所有非確定性行為（heartbeat 改為手動觸發、
  動畫關閉、async render 等同步化），讓測試可重現

** 九、Backend Conventions

本節描述 Backend（SBCL）端的軟性慣例，**不屬於線協議**。線協議完整定義
在 §四到 §七。這裡的東西讓不同的 Limn user code 看起來一致、互通；
若換成別的 backend 語言（理論上可以）也該照樣實作這些慣例。

*** 9.1 Mode 系統

Mode 是 Backend 端的物件，包含：

- 名稱（字串；慣例小寫加 =-mode= 後綴，例如 =pdf-mode=、=search-mode=）
- type：=:major= 或 =:minor=
- keymap（可指向 parent keymap，繼承綁定）
- 可選 =:on-enter= / =:on-exit= hook
- 可選 =:modeline-name=（modeline 顯示用，預設取 mode 名）

每個 buffer 有：
- 恰好一個 major mode
- 一個有序的 minor mode list（由近期啟用到最早啟用）

按鍵查詢順序：
1. buffer 的 minor modes（依啟用順序由新到舊）
2. buffer 的 major mode
3. global keymap

啟用 / 切換 mode 時 backend 應：
1. 觸發舊 mode 的 =:on-exit= hook（若是替換 major mode）
2. 啟動新 mode 的 keymap
3. 觸發新 mode 的 =:on-enter= hook
4. 呼叫 =modeline/set= 更新 modeline 顯示

Mode 與 engine 不同：engine 決定 buffer **裝什麼內容**（PDF、HTML、純
文字），mode 決定 buffer **使用者怎麼互動**。同一個 PDF buffer 可以套
=pdf-mode= 或 =presentation-mode=，內容不變、互動規則換了。

**Mode-buffer 與 wire buffer-id 的對應**：

每個 wire-level buffer（=bridge/engine-load= 或 chrome 自動建立的）在
backend 端對應一個 mode-buffer 狀態。Backend runtime（=limn.lisp= 或
等價物）維護 =buffer-id (string) → mode-buffer (object)= 的映射：

- =bridge/engine-load= 成功 → runtime 建一個 mode-buffer、啟用 engine
  預設的 major mode（如 =mupdf= engine 預設 =pdf-mode=、=text= engine
  預設 =fundamental-mode=）
- =buffer/close= → runtime 移除對應 mode-buffer
- chrome buffer (=*minibuffer*=、=*messages*=、=*echo-area*=) 在
  runtime 啟動時自動建立、各自啟用預設 mode（如 =*minibuffer*= →
  =minibuffer-mode=）

按鍵分派：=key= 事件帶 =win-id= → runtime 查 window 的 active buffer-id
→ 對應的 mode-buffer → 走 §9.1 的 minor → major → global keymap stack。

這層映射是 backend convention、不在線協議內——frontend 對 mode 一無所
知，只透過 =modeline/set= 等 chrome 命令間接看到 mode 名。

*** 9.2 Interactive 規範

每個 command 應宣告它需要的輸入。Framework 自動從 minibuffer 拿輸入
填進 command 的參數，command body 不直接碰 minibuffer：

#+begin_src lisp
(defcommand my-search
  (:interactive "sSearch: "     ; s = 從 minibuffer 讀字串，prompt 為 "Search: "
   :mode pdf-mode)              ; 限定在 pdf-mode 才生效
  (lambda (query)
    (search-and-jump query)))
#+end_src

Interactive spec 字元（沿用 Emacs）：

| 字元 | 意義                                          |
|------+-----------------------------------------------|
| =s=  | 從 minibuffer 讀一行字串                      |
| =f=  | 讀 file path（未來：minibuffer + completion） |
| =p=  | 接收 prefix arg（如 =5g= 的 5）                |
| =r=  | region（未來）                                |

Command 可以無 interactive spec（不需要外部輸入時）。

*** 9.3 Init file

啟動時 backend 依序嘗試載入：

1. 環境變數 =$LIMN_INIT= 指定的檔案
2. =~/.limn/init.lisp=
3. =~/.config/limn/init.lisp=（XDG）

擇先存在者載入；都沒有則跳過、不視為錯誤。

Init file 用來定義 mode、綁鍵、加 hook、自訂行為。對應 Emacs 的
=~/.emacs= / =~/.emacs.d/init.el=。

*** 9.4 Introspection

Backend 必須提供下列查詢，讓使用者「即時問系統」：

| 函式                              | 對應 Emacs |
|-----------------------------------+------------|
| =(describe-key spec)=             | =C-h k=    |
| =(describe-command name)=         | =C-h f=    |
| =(where-is-command name)=         | =C-h w=    |
| =(list-modes &optional buffer)=   | =describe-mode= |

這層讓 Limn 變得可學習——任何 key、任何 command 都能即時問它「你是什麼」。
