* Contributing to Limn

本文件記錄 Limn codebase 的合作慣例——*不是* 線協議（那在 LIMN-SPEC.org
裡）、也不是哲學討論（那在會議紀錄裡），是「打字之前該知道的事」。

** 一、Git workflow

*** 1.1 一個 commit = 一個 logical unit

每個 commit 必須：
- 自身能 build 過、跑得起所有測試（unit + integration 都該綠）
- 對應一個可以講清楚的 change（一句話 subject + 一段 body）
- 不混 refactor + feature + bug fix——拆開

寫程式時可以多 commit 當 safety net；**push 之前** 用 =git rebase -i
HEAD~N= 整理成 logical units。fixup-style 修補用 =--fixup= +
=--autosquash=。

*Counter-example*：「fix typo」「actually compile」「revert」「revert
revert」這種 WIP dump，push 前要整成乾淨單元，否則整段歷史失去 bisect 價值。

*** 1.2 主線 + feature branches

主線是 ~main~。

**小改動**（單 commit 或兩三個相關 commits）：直接到 main，不開 branch。

**多 batches 的 feature**（像 v0.7 Mode + Chrome 那種一次 8 個 batch）：
切 feature branch、做完再合回 main：

#+begin_src bash
git checkout -b feature/v0.8-init-and-introspection main
# ... 多個 batch commits 進 branch ...
git checkout main
git merge --no-ff feature/v0.8-init-and-introspection \
  -m "v0.8: init.lisp + introspection (describe-key、where-is)"
git tag -a v0.8.0 -m "..."
git branch -d feature/v0.8-init-and-introspection
#+end_src

#+begin_quote
*已部分取代（2026-05-29）*：上例的「branch 名帶版本號（=feature/v0.8-…=）
+ 在分支上自封 =v0.8.0= tag」已不再適用。新制：**分支名用功能名、不帶
版本號；版本號 / tag / CHANGELOG 收攏一律在 merge 進 main 那一刻由整合者
發放**。=--no-ff= 不 squash（§1.3）仍然有效。詳見 =docs/versioning-policy.md=。
#+end_quote

*** 1.3 為什麼用 =--no-ff= merge 不用 squash

squash merge **主動丟失資訊**——把 N 個各自 bisect-able 的 commit 壓成
一個無法 bisect 的大 commit。對守紀律的 codebase（§1.1 規則生效）是退步。

「merge commits 讓 history 變捷運圖」這個刻板印象來自舊工具
（=git log --graph= ASCII art、=gitk= 古早 UI、GitHub network graph
早期版本）。現在 magit / lazygit / GitLens 都能優雅折疊 merged branch
顯示成主線+支線。

具體 =--no-ff= 的好處：
- main 看 =git log --first-parent= 是乾淨主線（每個 merge 是一個 feature）
- 攤開看（=git log= 或 magit）能看到 feature 內部所有 batch commits
- bisect 對「整個 feature 是哪一段引入 bug」可精確到 batch

*** 1.4 Tag 里程碑

每個 SPEC 路線圖 milestone（v0.7、v0.8、...）完成時打 annotated tag：

#+begin_src bash
git tag -a v0.X.0 -m "summary of what shipped"
#+end_src

之後 =git log v0.7.0..HEAD= 一秒看「ship 之後改了什麼」。

*** 1.5 不做的事

- ❌ Conventional Commits（=feat:= / =fix:= / =chore:=）——formalism 大、
  價值小、容易爭執分類。subject 寫人話更直接。
- ❌ 每個 commit 一個 ticket number——SPEC 章節編號（§5.4、§9.1 等）已
  經夠精確。
- ❌ rebase 已 push 的 commit——歷史不可變。

** 二、Commit message 規範

*** 2.1 Subject

- ≤ 70 字（=git log --oneline= 才不會切）
- 直敘、人話、不必動詞時態
- 可以是中文也可以英文，看當下哪個更精準

合適例子：
- =LIMN-SPEC v0.4：引入 Mode 與 Chrome primitives 為核心概念=
- =v0.7 batch 6: minibuffer commands + filter event routing — v0.7 完工=
- =Retire vim PoC: framework loop proven, drop feature-specific code=

*** 2.2 Body

寫 *why* 不只 *what*——diff 已經顯示 what。Body 該包含：
- 這個 change 的動機（什麼問題、什麼洞察）
- 取捨點（為什麼這樣做不那樣做）
- 「刻意還沒做」的清單（防止下次自己忘了在哪、為什麼留個洞）
- 驗證方式 / 測試結果（讓 reviewer 一眼看到「我跑過、過了」）

不必寫的：什麼 file 改了什麼 line——diff 自己會講。

*** 2.3 Heredoc 範本

#+begin_src bash
git commit -m "$(cat <<'EOF'
<one-line subject ≤ 70 chars>

<開頭一段：問題 / 動機>

<過程或細節，用 markdown-ish 條列或段落>

<取捨點>

<刻意還沒做 / TODO>

<驗證：unit X/X、integration Y/Y、self-test 結果>
EOF
)"
#+end_src

** 三、測試紀律

*** 3.1 TDD 順序：spec → test → code

開發每一塊新東西：
1. SPEC 該怎麼描述（如有跨服務介面）
2. 寫測試讓它紅
3. 實作讓它綠
4. commit

紅測試本身值得獨立 commit（=v0.7 紅測試= 這個 commit 就是樣板）。

*** 3.2 跑哪些

#+begin_src bash
# 一鍵跑全部四層（推薦）
bash backend/tests/run-all-tiers.sh

# 跳過最慢的 os-e2e（不需要 docker 起來時）
bash backend/tests/run-all-tiers.sh --no-os

# 個別跑
nix develop --command sbcl --script backend/tests/unit/run-unit.lisp   # 秒級
nix develop --command bash backend/tests/run-tests.sh                  # 30 秒
bash backend/tests/e2e/run-e2e.sh                                       # 30 秒
docker run --rm limn-e2e                                                # 1 分鐘
#+end_src

四個都該綠才 commit。

**四層各自負責什麼**：

| 層          | 驅動                                | 覆蓋                                       |
|-------------+-------------------------------------+--------------------------------------------|
| unit        | mock client（in-memory FIFO）         | 純 Lisp 邏輯、各 module 隔離               |
| integration | 真 limn binary、raw JSON wire        | C++ 端 + bridge 協議                       |
| qt-e2e      | 真 limn binary、真 backend Lisp client、Qt-level inject | Qt event filter ↓ 整條 Lisp 鏈 |
| os-e2e      | container 內、Xvfb + xdotool、real X11 events | 加上 OS HID → AppKit-equiv → Qt 那段     |

unit + integration 都刻意避開 =limn.lisp / limn/cmd / limn/runtime=。
qt-e2e 補這個缺口。os-e2e 再補「真實 OS keystroke」那層。**新加跨模組
功能時**寫 e2e driver pair（=batch*-qt.lisp= + =batch*-os.lisp=），存到
=backend/tests/e2e/=。細節見該目錄 README。

**OS-level e2e 怎麼跑**：

container 用 nix-based Debian image（=Dockerfile= 在 repo 根目錄）。
=nixos/nix:latest= base + flake.nix 提供 Qt 6.11 / mupdf 1.27+，跟
macOS dev shell 完全同版本。container 內 Xvfb + xdotool + sbcl 全
nix-managed。

#+begin_src bash
# build (~5-10 分鐘第一次、後續 layer cache)
docker build -t limn-e2e .

# run e2e (~1 分鐘)
docker run --rm limn-e2e

# live debug (看 container 內 Limn 視窗、xdotool 按下去你看得到)
docker run --rm -it -p 5900:5900 -e X11VNC=1 limn-e2e bash
# 然後在 host：finder → 連線到伺服器 → vnc://localhost:5900
#+end_src

**快參考：cache 與乾淨狀態的平衡**

預設 invocation pattern 已經同時達到「不重下載」+「每次乾淨狀態」：

| 動作             | 行為                                          | 重跑成本          |
|------------------+-----------------------------------------------+-------------------|
| =docker build=   | layer cache、flake.nix 沒變秒級命中           | 1 秒（cache）     |
| =docker run --rm= | =--rm= 確保 container 跑完銷毀、下次 fresh    | 12 秒（一次性）   |
| flake.nix 改動   | 只重 build nix-store layer (10 分鐘)、其它走 cache | 10 分鐘        |

**從零重 build**（極少需要——懷疑 image corrupted、或驗證 reproducibility）：

#+begin_src bash
docker image rm limn-e2e          # 釋放 ~3.77GB
docker builder prune --all        # 釋放 ~30GB build cache
docker build -t limn-e2e .        # 從零 (~10 分鐘 + 全下載)
#+end_src

Docker Desktop 整個 Linux state 存在 =~/Library/Containers/com.docker.docker/Data/vms/0/data/Docker.raw=（sparse 60GB）。

**Build cache（ccache）—— 加速 + 風險與逃生**

容器內的 C++ 編譯走 ccache、cache 放在 buildkit 的 exec-cachemount
（持久於 docker daemon、不在 image layer 裡）。沒這層 cache 時每
次 incremental build 都要重編 ~80 個 .cpp，~3–5 分鐘；有的話只
重編真正變動的 ~10–15 秒。

ccache 的 key 是「(compiler 完整版本 + 全部 flags + preprocessed
source 的 hash)」，*不看* mtime、不看 file path、不看 git branch。
所以下面這些一般會把 .o 用爛的場景，ccache 全部繞掉：

- =docker COPY= 沒保留 host 的 mtime
- =git checkout= 跳 branch 把檔案時間倒退
- 多個 worktree 同時 build
- header 微改但某個 .cpp 沒被 Make 看見

但有兩種雷它沒蓋到、debug 時要主動懷疑：

1. *Toolchain 升 major version*：clang 21 → 22 時 hash key 自動變、
   舊 .o 不會被誤用、但會出現 cache 全 miss → 一次 full rebuild。
   *不會* 出錯、只是慢一次。
2. *ccache 本身的 bug / cache 檔案損毀*：罕見、但發生過。symptom
   通常很怪 —— undefined symbol、Qt segfault、test on host vs in
   container 結果不一致、「我明明改了還是沒生效」迴圈。

碰到 (2) 的 debug playbook：

#+begin_src bash
# Step 1: 證明它是 cache 問題、不是真 bug。
bash scripts/nuke-build-cache.sh
docker build --no-cache -t limn-e2e .
# 重跑你原本失敗的測試或操作。

# 若還是壞 → 真的是 code bug、放心去 debug。
# 若 nuke 完就好 → 寫進 commit message / CHANGELOG，
# 並考慮 file ccache upstream issue。
#+end_src

=scripts/nuke-build-cache.sh= 只清 ccache mount、不動 nix-store /
layer cache / image，所以下次重 build 只多 ~3-5 分鐘 ccache 重建、
不用重下載 nixpkgs 或重新 install Xvfb 等。

Dockerfile 對應段落也有同樣警語、debug 時眼睛先掃 build 步驟的
那一坨 banner 提醒。

*絕對不要 `touch -d <未來日期>` source 檔案*。理由：
- =docker COPY= 會保留 host 檔案的 mtime 進 image
- make 拿未來 mtime 比 Makefile mtime → 永遠覺得 source 比較新 →
  無限重跑 qmake → build 永遠卡在 step #13、看起來像是「hang」
  但實際是 CPU 100% 在跑 qmake loop
- 即使 host 上 =touch= 修回 mtime 也沒用，因為 docker COPY 的
  layer cache 是 *content-based*、檔案內容沒變就重用 cached layer
- 唯一修法：實際改檔案內容（例如加一行 comment）來 bust COPY cache
這個雷踩過一次、花了 ~30 分鐘 debug。原始觸發是想 bypass macOS host
上的 qmake xcode-license 錯誤、應該用其它解法（如 `nix develop --command make`
直接跳過 qmake regen）。

Macros / xdotool 命令參考見 =backend/tests/e2e/batch-os-*.lisp= 內的
=xdotool= helper（=sb-ext:run-program= 包 xdotool key/mouse 等）。

*** 3.3 自驗 GUI 改動

任何動到 Qt 的 commit，**作者自己** 跑一次 =test/inject-qt-key= +
=test/grab-window= 端到端驗證。寫 self-test script 放 =/tmp/=（不入庫）
跑一次，把結果摘要寫進 commit body。

不要等使用者當白老鼠。

** 四、其他

*** 4.1 「刻意還沒做」要明寫

Commit body 留下「v0.7 還沒做的」清單，下次 sprint 一眼接得上。code 裡
也行——用 =;; TODO (v0.X):= 標。

*** 4.2 命名

- engine 名：小寫加連字號（=mupdf=、=text=、=web=）
- mode 名：小寫加 =-mode=（=pdf-mode=、=search-mode=）
- 保留 buffer-id：星號夾（=*minibuffer*=、=*messages*=）

*** 4.3 SPEC 改動格外小心

LIMN-SPEC.org 是合約。改它影響所有實作者。改動規矩：
1. 先把 diff 列給 reviewer 過稿
2. 確認沒有 backward-incompatible 才動筆
3. 改完 commit 訊息標清楚 §X.Y 哪裡動了
4. 如果 break 已有實作，bump SPEC 版本（v0.3 → v0.4）

*** 4.4 不要動 sioyek 原碼

新功能加在新檔（=limn_*.cpp/h=）。sioyek 自己的 cpp/h 不動或極少動。
這個慣例從 PoC 階段就建立、要守。
