* Contributing to Limn

本文件記錄 Limn codebase 的合作慣例——*不是* 線協議（那在 LIMN-SPEC.org
裡）、也不是哲學討論（那在會議紀錄裡），是「打字之前該知道的事」。

** 一、Git workflow

*** 1.1 一個 commit = 一個 logical unit

每個 commit 必須：
- 自身能 build 過、跑得起所有測試（unit + integration 都該綠）
- 對應一個可以講清楚的 change（一句話 subject + 一段 body）
- 不混 refactor + feature + bug fix——拆開

寫程式時可以多 commit 當 safety net；**push 之前** 用 =git rebase -i
HEAD~N= 整理成 logical units。fixup-style 修補用 =--fixup= +
=--autosquash=。

*Counter-example*：「fix typo」「actually compile」「revert」「revert
revert」這種 WIP dump，push 前要整成乾淨單元，否則整段歷史失去 bisect 價值。

*** 1.2 主線 + feature branches

主線是 ~main~。

**小改動**（單 commit 或兩三個相關 commits）：直接到 main，不開 branch。

**多 batches 的 feature**（像 v0.7 Mode + Chrome 那種一次 8 個 batch）：
切 feature branch、做完再合回 main：

#+begin_src bash
git checkout -b feature/v0.8-init-and-introspection main
# ... 多個 batch commits 進 branch ...
git checkout main
git merge --no-ff feature/v0.8-init-and-introspection \
  -m "v0.8: init.lisp + introspection (describe-key、where-is)"
git tag -a v0.8.0 -m "..."
git branch -d feature/v0.8-init-and-introspection
#+end_src

*** 1.3 為什麼用 =--no-ff= merge 不用 squash

squash merge **主動丟失資訊**——把 N 個各自 bisect-able 的 commit 壓成
一個無法 bisect 的大 commit。對守紀律的 codebase（§1.1 規則生效）是退步。

「merge commits 讓 history 變捷運圖」這個刻板印象來自舊工具
（=git log --graph= ASCII art、=gitk= 古早 UI、GitHub network graph
早期版本）。現在 magit / lazygit / GitLens 都能優雅折疊 merged branch
顯示成主線+支線。

具體 =--no-ff= 的好處：
- main 看 =git log --first-parent= 是乾淨主線（每個 merge 是一個 feature）
- 攤開看（=git log= 或 magit）能看到 feature 內部所有 batch commits
- bisect 對「整個 feature 是哪一段引入 bug」可精確到 batch

*** 1.4 Tag 里程碑

每個 SPEC 路線圖 milestone（v0.7、v0.8、...）完成時打 annotated tag：

#+begin_src bash
git tag -a v0.X.0 -m "summary of what shipped"
#+end_src

之後 =git log v0.7.0..HEAD= 一秒看「ship 之後改了什麼」。

*** 1.5 不做的事

- ❌ Conventional Commits（=feat:= / =fix:= / =chore:=）——formalism 大、
  價值小、容易爭執分類。subject 寫人話更直接。
- ❌ 每個 commit 一個 ticket number——SPEC 章節編號（§5.4、§9.1 等）已
  經夠精確。
- ❌ rebase 已 push 的 commit——歷史不可變。

** 二、Commit message 規範

*** 2.1 Subject

- ≤ 70 字（=git log --oneline= 才不會切）
- 直敘、人話、不必動詞時態
- 可以是中文也可以英文，看當下哪個更精準

合適例子：
- =LIMN-SPEC v0.4：引入 Mode 與 Chrome primitives 為核心概念=
- =v0.7 batch 6: minibuffer commands + filter event routing — v0.7 完工=
- =Retire vim PoC: framework loop proven, drop feature-specific code=

*** 2.2 Body

寫 *why* 不只 *what*——diff 已經顯示 what。Body 該包含：
- 這個 change 的動機（什麼問題、什麼洞察）
- 取捨點（為什麼這樣做不那樣做）
- 「刻意還沒做」的清單（防止下次自己忘了在哪、為什麼留個洞）
- 驗證方式 / 測試結果（讓 reviewer 一眼看到「我跑過、過了」）

不必寫的：什麼 file 改了什麼 line——diff 自己會講。

*** 2.3 Heredoc 範本

#+begin_src bash
git commit -m "$(cat <<'EOF'
<one-line subject ≤ 70 chars>

<開頭一段：問題 / 動機>

<過程或細節，用 markdown-ish 條列或段落>

<取捨點>

<刻意還沒做 / TODO>

<驗證：unit X/X、integration Y/Y、self-test 結果>
EOF
)"
#+end_src

** 三、測試紀律

*** 3.1 TDD 順序：spec → test → code

開發每一塊新東西：
1. SPEC 該怎麼描述（如有跨服務介面）
2. 寫測試讓它紅
3. 實作讓它綠
4. commit

紅測試本身值得獨立 commit（=v0.7 紅測試= 這個 commit 就是樣板）。

*** 3.2 跑哪些

#+begin_src bash
# unit (純 Lisp，秒級)
nix develop --command sbcl --script backend/tests/unit/run-unit.lisp

# integration (跑 limn binary，30 秒級)
nix develop --command bash backend/tests/run-tests.sh

# e2e (跑 limn binary + 真實 backend Lisp client，分鐘級)
bash backend/tests/e2e/run-e2e.sh
#+end_src

三個都該綠才 commit。

**三層各自負責什麼**：

| 層       | 驅動                         | 覆蓋                                       |
|----------+------------------------------+--------------------------------------------|
| unit     | mock client（in-memory FIFO） | 純 Lisp 邏輯、各 module 隔離               |
| integration | 真 limn binary、raw JSON wire | C++ 端 + bridge 協議                       |
| e2e      | 真 limn binary、真 backend Lisp client | 使用者實際走的鏈條（key → command → ...） |

unit + integration 都刻意避開 =limn.lisp / limn/cmd / limn/runtime=。
e2e 補這個缺口。**新加跨模組功能時**寫一個 e2e driver，存到
=backend/tests/e2e/batch*.lisp=（細節見該目錄 README）。

**已知限制 + 下一步**：當前 e2e 用 =test/inject-qt-key= 走 Qt-level
注入，覆蓋 Qt event filter 以下整條 Lisp 鏈，但 macOS HID → AppKit
→ QApplication 那段沒測。macOS 上 OS-level 鍵盤注入需要 Accessibility
授權（=osascript=、=cliclick=），不適合 default suite。

下一個 implementation milestone（v0.9）整個焦點放在這層補完：

- Debian slim container（最小、Qt6 兼容性穩）
- Xvfb 虛擬 X server
- =xdotool= 提供 zero-permission OS-level keyboard / mouse / hover /
  scroll / window-focus 注入
- 每個既有 =batch*-qt.lisp= 寫一個 =batch*-os.lisp= 對等版
- =backend/tests/run-all-tiers.sh= 一鍵跑三層

container 化的好處：dev local + 任何 Linux runner 用同一個 image、
bit-exact 可重現。Local debug 可用 x11vnc 從 macOS Screen Sharing 連
=localhost:5900= 看 container 內 Limn 視窗真的被 xdotool 按。

注意：testing 基礎建設不在 LIMN-SPEC 範圍——SPEC 是產品合約（wire 協議、
runtime 行為），這層是開發過程。兩件事分家。

*** 3.3 自驗 GUI 改動

任何動到 Qt 的 commit，**作者自己** 跑一次 =test/inject-qt-key= +
=test/grab-window= 端到端驗證。寫 self-test script 放 =/tmp/=（不入庫）
跑一次，把結果摘要寫進 commit body。

不要等使用者當白老鼠。

** 四、其他

*** 4.1 「刻意還沒做」要明寫

Commit body 留下「v0.7 還沒做的」清單，下次 sprint 一眼接得上。code 裡
也行——用 =;; TODO (v0.X):= 標。

*** 4.2 命名

- engine 名：小寫加連字號（=mupdf=、=text=、=web=）
- mode 名：小寫加 =-mode=（=pdf-mode=、=search-mode=）
- 保留 buffer-id：星號夾（=*minibuffer*=、=*messages*=）

*** 4.3 SPEC 改動格外小心

LIMN-SPEC.org 是合約。改它影響所有實作者。改動規矩：
1. 先把 diff 列給 reviewer 過稿
2. 確認沒有 backward-incompatible 才動筆
3. 改完 commit 訊息標清楚 §X.Y 哪裡動了
4. 如果 break 已有實作，bump SPEC 版本（v0.3 → v0.4）

*** 4.4 不要動 sioyek 原碼

新功能加在新檔（=limn_*.cpp/h=）。sioyek 自己的 cpp/h 不動或極少動。
這個慣例從 PoC 階段就建立、要守。
